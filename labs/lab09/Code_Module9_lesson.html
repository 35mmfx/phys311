1   Modules: One File per Idea

1.1   A file layout that works

labs/lab09/
  index.html
  style.css
  main.js              // wiring only: build a scene, start the loop
  engine/
    vec2.js            // Vec2                (from Lab 8)
    body.js            // Body
    forces.js          // Gravity, Drag, Spring, NewtonGravity
    integrators.js     // EulerCromer, VelocityVerlet
    collisions.js      // detection + resolution
    world.js           // World: owns bodies, forces, integrator
  render/
    camera.js          // physics coords ↔ pixels  (from Lab 8)
    renderer.js        // all ctx.* drawing lives here
    hud.js             // diagnostics overlay
💡 The engine/ vs. render/ split is the most important line in this lesson. Nothing inside engine/ is allowed to mention canvas, ctx, or pixels. Nothing inside render/ is allowed to modify a body's state. If you keep that boundary clean, you can swap renderers, run headless tests, and reuse the whole engine in your final project. If you blur it, you'll be untangling it in Week 12 under deadline pressure.
⚠️ Module gotchas. The .js extension is required in import paths (unlike Python). Paths must start with ./ or ../. Modules are always strict mode, so undeclared variables throw errors — a feature, not a bug. And modules only work over HTTP: keep using Live Server.

2.1   World.step(dt) — the whole engine in eight lines

import { EulerCromer } from "./integrators.js";
import { resolveCollisions } from "./collisions.js";

export class World {
  constructor({ integrator = new EulerCromer(), bounds = null } = {}) {
    this.bodies = [];
    this.forces = [];
    this.integrator = integrator;
    this.bounds = bounds;       // {xMin, xMax, yMin, yMax} in meters
    this.time = 0;
    this.restitution = 0.9;
  }

  add(body)       { this.bodies.push(body); return body; }
  addForce(force) { this.forces.push(force); return force; }

  step(dt) {
    for (const b of this.bodies) b.clearForce();      // 1. reset
    for (const f of this.forces) f.apply(this);         // 2. accumulate
    this.integrator.step(this, dt);                   // 3. integrate
    resolveCollisions(this);                          // 4. collide
    this.time += dt;                                  // 5. advance clock
  }

  totalEnergy() {
    let E = 0;
    for (const b of this.bodies) E += b.kineticEnergy();
    for (const f of this.forces) E += f.potentialEnergy?.(this) ?? 0;
    return E;
  }

  totalMomentum() {
    const p = new Vec2();
    for (const b of this.bodies) p.addScaled(b.vel, b.m);
    return p;
  }
}
🔬 Recognize this? It is character-for-character the same five-stage loop as your Lab 7 World.step(). That's the payoff of building the Python prototype first: the hard design thinking was already done, and this week is transcription plus rendering. Note f.potentialEnergy?.(this) ?? 0 — JavaScript's optional-call and nullish-coalescing operators let forces opt in to reporting PE without every force needing the method.

2.2   Forces: the same polymorphism

export class Gravity {
  constructor(g = 9.81) { this.g = g; }
  apply(world) {
    for (const b of world.bodies) {
      if (b.isStatic) continue;
      b.force.y -= b.m * this.g;
    }
  }
  potentialEnergy(world) {
    let U = 0;
    for (const b of world.bodies) U += b.m * this.g * b.pos.y;
    return U;
  }
}

export class Drag {
  constructor(c = 0.1) { this.c = c; }
  apply(world) {
    for (const b of world.bodies) {
      const speed = b.vel.length();
      if (speed > 0) b.force.addScaled(b.vel, -this.c * speed);
    }
  }
  // no potentialEnergy — drag is non-conservative. That's the point.
}

export class NewtonGravity {
  constructor(G = 1, softening = 0.01) { this.G = G; this.eps = softening; }
  apply(world) {
    const bs = world.bodies;
    for (let i = 0; i < bs.length; i++) {
      for (let j = i + 1; j < bs.length; j++) {
        const d = bs[j].pos.sub(bs[i].pos);
        const r2 = d.lengthSq() + this.eps ** 2;
        const F = this.G * bs[i].m * bs[j].m / (r2 * Math.sqrt(r2));
        bs[i].force.addScaled(d,  F);
        bs[j].force.addScaled(d, -F);   // Newton's third law, for free
      }
    }
  }
}
⚠️ Softening isn't optional in the browser. Two bodies passing very close give r → 0 and a force → ∞, which sends a body to infinity in one frame and then to NaN. In Python you saw a bad plot; in a live animation the whole scene vanishes and never returns, because NaN propagates forever. The + eps² term caps the force at close range. Add it now.

2.3   Integrators as objects

export class EulerCromer {
  step(world, dt) {
    for (const b of world.bodies) {
      if (b.isStatic) continue;
      b.acc.set(b.force.x / b.m, b.force.y / b.m);
      b.vel.addScaled(b.acc, dt);      // velocity first
      b.pos.addScaled(b.vel, dt);      // then position
    }
  }
}

export class VelocityVerlet {
  step(world, dt) {
    // half-kick, drift, recompute forces, half-kick
    for (const b of world.bodies) {
      if (b.isStatic) continue;
      b.acc.set(b.force.x / b.m, b.force.y / b.m);
      b.vel.addScaled(b.acc, 0.5 * dt);
      b.pos.addScaled(b.vel, dt);
    }
    for (const b of world.bodies) b.clearForce();
    for (const f of world.forces) f.apply(world);
    for (const b of world.bodies) {
      if (b.isStatic) continue;
      b.acc.set(b.force.x / b.m, b.force.y / b.m);
      b.vel.addScaled(b.acc, 0.5 * dt);
    }
  }
}
💡 Swapping integrators is now one line: world.integrator = new VelocityVerlet();. That's the whole reason for the object wrapper. In Week 10 you'll wire it to a dropdown and let users flip it mid-simulation — turning your Week 2 integrator comparison into something anyone can play with.

3   The Collision Pipeline, Live

Week 4 gave you the physics. Now it runs 120 times a second, so the structure matters:

PhaseQuestionCost
BroadWhich pairs might be touching?Cheap — reject most pairs fast
NarrowAre they actually overlapping, and by how much?Moderate — exact test
ResolutionSeparate them, then apply the impulseCheap — but order matters

3.1   Circle–circle resolution

export function resolvePair(a, b, e = 0.9) {
  const d = b.pos.sub(a.pos);
  const distSq = d.lengthSq();
  const rSum = a.radius + b.radius;
  if (distSq >= rSum * rSum || distSq === 0) return false;   // no contact

  const dist = Math.sqrt(distSq);
  const n = d.mul(1 / dist);            // unit normal, a → b

  // --- 1. Positional correction: push them apart (no overlap!) ---
  const overlap = rSum - dist;
  const invA = a.isStatic ? 0 : 1 / a.m;
  const invB = b.isStatic ? 0 : 1 / b.m;
  const invSum = invA + invB;
  if (invSum === 0) return false;          // two static bodies
  a.pos.addScaled(n, -overlap * (invA / invSum));
  b.pos.addScaled(n,  overlap * (invB / invSum));

  // --- 2. Impulse: only if they're approaching ---
  const relVel = b.vel.sub(a.vel);
  const vn = relVel.dot(n);
  if (vn > 0) return true;                // separating — leave alone

  const J = -(1 + e) * vn / invSum;      // impulse magnitude
  a.vel.addScaled(n, -J * invA);
  b.vel.addScaled(n,  J * invB);
  return true;
}
⚠️ The if (vn > 0) return guard is essential. Without it, bodies that are overlapping but already moving apart get hit with another impulse, which shoves them back together. The result is the classic "jitter" — objects vibrating and buzzing instead of resting. This one line is the difference between a demo that looks professional and one that looks broken.
🔬 Why separate positional correction from the impulse? They fix different errors. Position correction fixes a discretization artifact — the bodies overlap only because we stepped past the true contact instant. The impulse is the physics — it enforces the restitution law from Week 4. Conflating them (a common shortcut) either leaves objects sinking into each other or injects fake energy.

3.2   Broad phase: when O(n²) stops being fine

Checking all pairs is n(n−1)/2 tests. At 120 physics steps per second:

BodiesPairs / stepTests / secondVerdict
20190~23,000Trivial
1004,950~594,000Fine
500124,750~15,000,000Starting to hurt
20001,999,000~240,000,000Unusable

If you need more than a few hundred bodies, add a uniform grid: bucket bodies by cell, test only within a cell and its neighbors.

export function gridPairs(bodies, cellSize) {
  const cells = new Map();
  const key = (i, j) => `${i},${j}`;

  for (const b of bodies) {
    const i = Math.floor(b.pos.x / cellSize);
    const j = Math.floor(b.pos.y / cellSize);
    const k = key(i, j);
    if (!cells.has(k)) cells.set(k, []);
    cells.get(k).push(b);
    b._ci = i; b._cj = j;
  }

  const pairs = [];
  for (const b of bodies) {
    for (let di = -1; di <= 1; di++)
      for (let dj = -1; dj <= 1; dj++) {
        const bucket = cells.get(key(b._ci + di, b._cj + dj));
        if (!bucket) continue;
        for (const o of bucket) if (b !== o && b.id < o.id) pairs.push([b, o]);
      }
  }
  return pairs;
}
💡 Choose cellSize ≈ 2× the largest body radius. Too small and bodies span many cells; too large and every body lands in the same bucket, giving you O(n²) with extra bookkeeping. And note: don't build this until you measure that you need it. Profile first (§5), optimize second.

3.3   Tunneling: the bug that only appears in real time

A fast body can move past a thin wall in a single step, so the overlap test never fires and it sails straight through. This is tunneling, and it's the most common "my collisions randomly fail" complaint.

Tunneling occurs when |v| · Δt > (body diameter + wall thickness)
FixCostWhen to use
Smaller DT (e.g. 1/240)More steps/frameSimplest; usually enough
Thicker wallsFreeAlways do this — make walls at least a body-diameter thick
Speed cap on bodiesFree, slightly unphysicalGames; document that you did it
Swept / continuous detectionComplexOnly if you truly need bullets
✍️ Try it: With DT = 1/60 and a body of radius 0.2 m, at what speed does it start tunneling through a 0.1 m-thick wall? Compute it, then verify in your simulation by ramping the launch speed until the body escapes. Predicting a bug before you see it is the mark of understanding the method.

4   The Renderer and the Live HUD

The renderer's contract: read the world, write to the canvas, change nothing.

export class Renderer {
  constructor(canvas, camera) {
    this.ctx = canvas.getContext("2d");
    this.canvas = canvas;
    this.camera = camera;
  }

  draw(world) {
    const { ctx, canvas, camera } = this;
    ctx.clearRect(0, 0, canvas.width, canvas.height);

    for (const b of world.bodies) {
      const p = camera.toScreen(b.pos);
      ctx.fillStyle = b.color ?? "#ff8200";
      ctx.beginPath();
      ctx.arc(p.x, p.y, b.radius * camera.scale, 0, 2 * Math.PI);
      ctx.fill();
    }
  }
}

4.1   Conservation laws as a live readout

export function drawHUD(ctx, world, E0, p0) {
  const E = world.totalEnergy();
  const p = world.totalMomentum();
  const dE = E0 === 0 ? 0 : (E - E0) / Math.abs(E0);

  const lines = [
    `t        = ${world.time.toFixed(2)} s`,
    `bodies   = ${world.bodies.length}`,
    `E        = ${E.toFixed(4)} J`,
    `dE/E0    = ${(dE * 100).toFixed(3)} %`,
    `|p|      = ${p.length().toFixed(4)}`,
  ];

  ctx.font = "13px monospace";
  ctx.fillStyle = Math.abs(dE) > 0.01 ? "#dc3545" : "#2d3b45";  // red if drifting!
  lines.forEach((line, i) => ctx.fillText(line, 12, 20 + i * 17));
}
💡 Turning the HUD red past 1% drift is the single best debugging feature you can build. It's your entire Block 1 validation philosophy compressed into one visual signal, running continuously. You'll catch bugs in seconds that would take a full Python run and a plot to notice — and a viewer of your final project can see, at a glance, that your physics is honest.
🔬 Which law catches which bug. Momentum is the sharpest collision test: with no external forces, |p| must be constant to round-off through any number of collisions. If it jumps, your impulse is asymmetric — you applied it to one body and not the other, or used the wrong sign. Energy catches integrator problems and, with e = 1, catches collision-code errors that momentum can't see.

5   Performance: Measure, Then Optimize

You have a 16.7 ms budget per frame at 60 fps. Physics, collisions, and rendering all share it.

const t0 = performance.now();
while (acc >= DT) { world.step(DT); acc -= DT; }
const tPhysics = performance.now() - t0;

const t1 = performance.now();
renderer.draw(world);
const tRender = performance.now() - t1;

Display both on the HUD. Now you know where the time actually goes — and students are usually surprised.

SymptomLikely causeFix
Physics time dominatesO(n²) pair loopsSpatial grid (§3.2)
Render time dominatesToo many beginPath/state changes; huge trailsBatch by color; cap trail length
Smooth, then sudden stutterGarbage collectionUse in-place Vec2 ops in the hot loop
Everything freezes permanentlyNaN in a positionAdd softening; guard divide-by-zero; check with Number.isFinite
⚠️ NaN is permanent. Any arithmetic involving NaN produces NaN, so one bad division silently corrupts a body forever and it simply disappears from the screen. Add a guard during development: 
if (!Number.isFinite(b.pos.x) || !Number.isFinite(b.pos.y)) {
  console.error("NaN body!", b);
  debugger;   // pauses execution so you can inspect state
}
✍️ Try it: Build a scene with 50 bouncing balls and read your physics/render timings. Now bump it to 200 and to 500. Where does the frame budget break? Which number grew faster — physics or render? Predict the answer before you measure.
