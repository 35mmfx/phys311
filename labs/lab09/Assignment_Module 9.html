Part A — The Modular Engine (30 points)

GUIDED — Follow the Lesson

What to do

  1. Build the module structure from the lesson: engine/ containing vec2.js, body.js, forces.js, integrators.js, collisions.js, world.js; render/ containing camera.js, renderer.js, hud.js.
  2. Implement World with bodies[], forces[], a swappable integrator, and a step(dt) that runs the five-stage loop: clear forces → apply forces → integrate → resolve collisions → advance time.
  3. Implement at least three forces, each with an apply(world) method: Gravity (uniform), plus two of Drag / Spring / NewtonGravity. Give conservative forces a potentialEnergy(world) method.
  4. Implement both integrators (EulerCromer, VelocityVerlet) sharing a step(world, dt) signature.
  5. Implement the renderer in render/renderer.js. Enforce the rule: no file in engine/ mentions canvas, ctx, or pixels.
  6. Keep main.js thin — it should only construct a scene, build the world, and run the accumulator loop.
⚠️ The layering rule is graded and is checked by inspection. Search your engine/ folder for the strings ctx, canvas, and document. If any appear, you have a violation. The test that matters: could you run your engine in a Node script with no browser at all? It should be yes.
💡 Hint: giving bodies stable IDs

Collision code and the grid broad phase both need to avoid testing a pair twice. Give each body a unique integer at construction:

let _nextId = 0;
export class Body {
  constructor(opts) { this.id = _nextId++; /* ... */ }
}

Then if (a.id < b.id) guarantees each pair is considered exactly once.

Part B — Collisions and Live Validation (35 points)

GUIDED → INDEPENDENT

B1 — The collision pipeline (18 pts)

  1. Implement wall collisions against world bounds, with restitution and positional correction (clamp the position, then reflect the velocity).
  2. Implement circle–circle collisions with the three required pieces from the lesson: positional correction weighted by inverse mass, the vn > 0 separating guard, and the restitution impulse.
  3. Support static bodies via an isStatic flag (treated as infinite mass — inverse mass zero). Use one as an immovable obstacle in a scene.
  4. Demonstrate the jitter bug deliberately. Comment out the vn > 0 guard, record what happens (screenshot or 5-second recording), restore it. Explain in 2–3 sentences why the guard fixes it.

B2 — The conservation HUD (17 pts)

  1. Display live: t, body count, E_total, fractional drift (E − E₀)/|E₀| as a percentage, |p|, fps, and physics-vs-render timing in ms.
  2. Color-code the drift — turn the readout red when |ΔE/E₀| exceeds 1%.
  3. Run the momentum test: build a scene with no external forces (no gravity), e = 1, and 20 balls in a box. Total momentum must stay constant to round-off through hundreds of collisions. Report |p| at t = 0 and t = 60 s.
  4. Run the energy test: same scene, e = 1. Report E_total at t = 0 and t = 60 s and the fractional drift.
  5. Then set e = 0.8 and confirm energy now decreases monotonically while momentum is still conserved. Explain in 2–3 sentences why the two laws behave differently.
🔬 This is the sharpest test in the whole course. In an isolated box with elastic collisions, momentum conservation is exact — not approximate. Round-off only. If your |p| drifts even in the third decimal, you have a genuine asymmetry in your impulse code, and no amount of "it looks right" fixes that. Chase it down.
⚠️ Careful with e = 1 plus gravity. Positional correction slightly changes potential energy, so a perfectly elastic ball bouncing under gravity can creep upward or downward over time. That's why the momentum and energy tests above specify no gravity — it isolates the collision code from the integrator. Test one thing at a time; that's the Block 1 lesson applied.

Requirements for all three

  1. Same engine, zero changes. Scenes live in main.js (or a scenes.js outside engine/). If you had to modify an engine file to make a scene work, say so honestly in the write-up and explain what the design missed — honest analysis earns most of the credit back.
  2. Runtime integrator switch available in every scene.
  3. The HUD is visible and accurate in every scene.
  4. Scene 2 must run for at least 60 seconds without a body escaping to infinity or producing NaN. If it does, fix your softening and time step — don't just restart it.

Performance report (required)

  1. Scale Scene 1 to 20, 50, 100, and 200 bodies. Record physics ms, render ms, and fps for each.
  2. Present a table and identify the bottleneck. Which grew faster, and does that match the O(n²) prediction from the lesson?
  3. State the largest body count your machine sustains at 60 fps, and what you would optimize first to raise it.

⭐ Bonus — Choose One (up to 10 points)

  • Spatial grid broad phase (10 pts). Implement the uniform grid from the lesson. Show a before/after timing table at 200 and 500 bodies, and report the speedup. Verify the grid version produces the same physics (momentum still conserved).
  • Rotational bodies (10 pts). Port your Week 6 rigid-body work: add theta, omega, I, and torque to Body; draw a radius line so rotation is visible; add angular momentum to the HUD and demonstrate it's conserved for a torque-free scene.
  • Deterministic replay (10 pts). Add a seeded pseudo-random generator and a "replay" button that re-runs a scene from identical initial conditions. Show that two runs produce bit-identical final states — the ultimate proof your fixed timestep works.
