2   The Game Loop & Fixed Timestep

Every physics engine, from yours to Unity, runs a loop: compute forces → integrate → handle collisions → (render) → repeat. The critical design rule:

💡 Use a fixed timestep for physics. Always advance the physics by the same small dt, no matter how fast the display runs. Variable timesteps make simulations non-reproducible and can blow up when a frame lags. In Block 3, you'll render at the browser's frame rate but still step physics at a fixed dt — a pattern called the "accumulator." Build the habit now. 
while running:
    compute_all_forces()     # sum forces on every body
    integrator.step(dt)      # advance state by fixed dt
    handle_collisions()      # detect and resolve
    record_or_render()       # store data (Python) or draw (JS later)

└───┬─────────┬─────────┬───────────┘
    │       │        │
  Body   Force   Integrator

3.1   The Body

import numpy as np

class Body:
    def __init__(self, mass, pos, vel, radius=0.1, I=None):
        self.m = mass
        self.r = np.array(pos, dtype=float)
        self.v = np.array(vel, dtype=float)
        self.radius = radius
        self.theta = 0.0      # orientation
        self.omega = 0.0      # angular velocity
        self.I = I if I is not None else 0.5*mass*radius**2
        self.force = np.zeros(2)   # accumulator, reset each step
        self.torque = 0.0

    def clear_accumulators(self):
        self.force = np.zeros(2)
        self.torque = 0.0

3.2   Forces (the registry pattern)

Each force is an object that knows how to apply itself to the bodies in the world. The world holds a list of them, so adding gravity, drag, or a spring is just appending to that list.

class Gravity:
    def __init__(self, g=9.81):
        self.g = np.array([0.0, -g])
    def apply(self, world):
        for b in world.bodies:
            b.force += b.m * self.g        # F = mg

class Drag:
    def __init__(self, c):
        self.c = c
    def apply(self, world):
        for b in world.bodies:
            b.force += -self.c * np.linalg.norm(b.v) * b.v   # quadratic drag
💡 Why this is powerful: to change the physics of your simulation, you change the list of forces, not the loop. Want an orbit? Add a NewtonGravity force. Want a damped oscillator? Add a Spring and a Drag. The engine core never changes. This is the "open–closed principle" — open to extension, closed to modification.

3.3   The Integrator (swappable)

class EulerCromer:
    def step(self, world, dt):
        for b in world.bodies:
            a = b.force / b.m
            b.v += a * dt
            b.r += b.v * dt
            alpha = b.torque / b.I
            b.omega += alpha * dt
            b.theta += b.omega * dt
🔬 This is Lab 2's swap, promoted to architecture. Back in Lab 2 you switched Euler for Euler-Cromer by changing one function. Now the integrator is an object you hand to the world. Swapping to Verlet for an orbit simulation means constructing a different integrator — zero changes to bodies or forces.

3.4   The World (ties it together)

class World:
    def __init__(self, integrator):
        self.bodies = []
        self.forces = []
        self.integrator = integrator
        self.time = 0.0

    def add_body(self, body):  self.bodies.append(body)
    def add_force(self, force): self.forces.append(force)

    def step(self, dt):
        for b in self.bodies:
            b.clear_accumulators()
        for f in self.forces:
            f.apply(self)                 # each force adds to body accumulators
        self.integrator.step(self, dt)    # advance state
        self.handle_collisions()          # detect + resolve
        self.time += dt

    def handle_collisions(self):
        pass   # fill in using your Lab 4 collision code
✍️ Try it: Reproduce Lab 1's projectile in six lines — world = World(EulerCromer()); world.add_body(Body(1, [0,0], [15,20])); world.add_force(Gravity()), then loop world.step(0.01) and record positions. If your old lab and your new engine agree, your architecture is sound.

4   The Collision Pipeline

Real engines split collision handling into stages for efficiency and clarity:

Overview of collision detection and resolution stages with implementation details
StageJobYour implementation
Broad phaseQuickly rule out pairs that can't collideFor now, just loop all pairs (fine for tens of bodies)
Narrow phasePrecisely detect overlapsYour circle–circle test from Lab 4
ResolutionCompute new velocitiesYour collide_2d from Lab 4
🔬 Broad phase is an optimization, not physics. Checking all pairs is O(N²). For thousands of bodies, engines use spatial grids or trees to cut this down. You don't need that yet — but knowing the pipeline has a "broad phase" slot means you can drop in an optimization later without touching the physics.

5   Testing Your Engine

💡 Your conservation laws are your regression tests. Because your engine is modular, you can test each piece against a lab you already trust: projectile (Lab 1–2), oscillator (Lab 3), collisions (Lab 4), orbit (Lab 5), rotation (Lab 6). If the engine reproduces all six with the right conservation behavior, it's correct. Keep these as automated checks.
⚠️ Resist over-engineering. You do not need inheritance hierarchies, abstract base classes, or a plugin system. Four clean classes and a list of forces is enough to carry you through the final project. Clarity beats cleverness — you'll be porting this to JavaScript, and simple designs port more easily.
