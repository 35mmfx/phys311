1   Events: How the Browser Talks to You

Python code you wrote ran top to bottom. Browser code is event-driven: you register callbacks and the browser calls them when something happens.

canvas.addEventListener("pointerdown", (event) => {
  console.log("clicked at", event.clientX, event.clientY);
});

💡 Use pointer* events, not mouse*. Pointer events unify mouse, touch, and stylus in a single API. Write them once and your simulation works on a phone with no extra code. Since your project will be shared publicly — and a good fraction of visitors will be on phones — this is a five-character decision with a big payoff.

1.1   Getting the click into physics coordinates

Event coordinates are relative to the browser viewport, not your canvas. Two conversions are needed:

function eventToWorld(event, canvas, camera) {
  const rect = canvas.getBoundingClientRect();

  // 1. viewport → canvas pixels (the ratio handles CSS scaling)
  const px = (event.clientX - rect.left) * (canvas.width  / rect.width);
  const py = (event.clientY - rect.top ) * (canvas.height / rect.height);

  // 2. canvas pixels → physics meters (this is your Lab 8 camera, inverted)
  return camera.toWorld(px, py);
}
⚠️ Skip the rect.width ratio and your clicks will be offset. If CSS ever displays your canvas at a size different from its drawing buffer — which responsive layouts do constantly — raw clientX lands in the wrong place, and the error grows with distance from the top-left. Symptom: "grabbing works near the corner but not across the screen." This ratio is the fix.

1.2   Keyboard: track state, don't act on the event

For continuous input like thrust, don't apply force inside the event handler — the OS key-repeat rate is not your physics rate. Record which keys are down, and read that state inside the fixed step:

const keys = new Set();
window.addEventListener("keydown", e => {
  keys.add(e.code);
  if (["Space", "ArrowUp", "ArrowDown"].includes(e.code)) e.preventDefault();
});
window.addEventListener("keyup", e => keys.delete(e.code));

// Inside world.step() — a Force like any other
class ThrustForce {
  constructor(body, keys, magnitude) { /* ... */ }
  apply(world) {
    if (this.keys.has("ArrowUp"))    this.body.force.y += this.mag;
    if (this.keys.has("ArrowLeft"))  this.body.force.x -= this.mag;
    if (this.keys.has("ArrowRight")) this.body.force.x += this.mag;
  }
}
🔬 Notice what just happened. User input became a Force object — same interface as Gravity and Drag, registered the same way, consumed by the same accumulator. Your Week 7 architecture absorbed interactivity without a single structural change. That is what good design buys you.

2   Manipulating Bodies with the Mouse

2.1   Picking

function bodyAt(world, worldPos) {
  for (let i = world.bodies.length - 1; i >= 0; i--) {   // topmost first
    const b = world.bodies[i];
    const pick = Math.max(b.radius, 0.25);   // generous target for touch
    if (b.pos.sub(worldPos).lengthSq() <= pick * pick) return b;
  }
  return null;
}

2.2   Two ways to drag — and why one is much better

Comparison of teleporting and spring-based cursor control for a body, including implementation and physical consequences.
ApproachHowConsequence
TeleportSet body.pos to the cursor each frameBodies pass through walls; releasing gives zero or absurd velocity; energy meaningless
Spring to cursor ✓Add a damped spring force pulling the body toward the cursorCollisions still work, release velocity is physical, and it feels right
 
class MouseSpring {
  constructor() { this.body = null; this.target = null; this.k = 200; this.c = 20; }

  apply(world) {
    if (!this.body || !this.target) return;
    const d = this.target.sub(this.body.pos);
    this.body.force.addScaled(d, this.k * this.body.m);        // spring
    this.body.force.addScaled(this.body.vel, -this.c * this.body.m); // damping
  }
}
⚠️ A stiff spring plus a large DT explodes. Stability requires roughly Δt < 2/√(k/m). With k = 200 that means DT below about 0.14 s — fine at 1/120, but if you let users crank a stiffness slider without bounding it, they'll launch bodies to infinity. Always clamp slider ranges to stable values, and mention the stability limit in your write-up. This is your Week 1–3 step-size analysis showing up as a UI design constraint.

2.3   Slingshot launching

The most satisfying interaction you can build in an afternoon: press to place, drag to aim, release to launch.

let aimStart = null;

canvas.addEventListener("pointerdown", e => { aimStart = eventToWorld(e, canvas, camera); });
canvas.addEventListener("pointerup", e => {
  if (!aimStart) return;
  const end = eventToWorld(e, canvas, camera);
  const v = aimStart.sub(end).mul(2.0);       // pull back = launch forward
  world.add(new Body({ pos: aimStart, vel: v, m: 1, radius: 0.2 }));
  aimStart = null;
});

While aiming, draw the predicted trajectory — run a copy of the physics forward without committing it:

function predictPath(pos, vel, g, steps = 60, dt = 1/30) {
  const path = [];
  let p = pos.clone(), v = vel.clone();
  for (let i = 0; i < steps; i++) {
    v.y -= g * dt;  p.addScaled(v, dt);        // Euler-Cromer, on a copy
    path.push(p.clone());
  }
  return path;
}
🔬 A trajectory preview is physics education embedded in a UI. The user drags, sees the parabola change, and builds intuition about launch angle and range without reading a word. If you add drag to the real simulation but not the preview, the ball will miss the predicted path — which is itself a beautiful teaching moment. Consider making it a toggle: "preview with / without air resistance."

const gravSlider = document.getElementById("grav");
gravSlider.addEventListener("input", () => {
  const g = parseFloat(gravSlider.value);      // ALWAYS parse — .value is a string!
  gravity.g = g;
  document.getElementById("gravVal").textContent = g.toFixed(2);
});
⚠️ input.value is always a string. Forget parseFloat and "9.81" * 2 gives 19.62 (JS coerces) but "9.81" + 2 gives "9.812" (string concatenation). That mixed behavior produces bizarre, hard-to-trace physics bugs. Parse at the boundary, every time.

3.1   Pause, step, and reset — done correctly

let paused = false;
let stepOnce = false;
let speed = 1;               // 0.25 = slow-mo, 2 = fast-forward

function loop(ts) {
  if (!last) last = ts;
  const frame = Math.min((ts - last) / 1000, 0.25);
  last = ts;

  if (!paused) {
    acc += frame * speed;                // speed scales TIME, never DT
  } else if (stepOnce) {
    acc += DT;  stepOnce = false;         // advance exactly one step
  }

  while (acc >= DT) { world.step(DT); acc -= DT; }
  renderer.draw(world);
  requestAnimationFrame(loop);
}
💡 Speed control scales the accumulator, never DT. The tempting shortcut — world.step(DT * speed) — destroys the fixed timestep and everything it guarantees. Feeding the accumulator faster or slower means physics still advances in identical DT slices; you're just running more or fewer of them per real second. Slow-motion becomes a legitimate scientific instrument: you can watch a collision resolve step by step and still trust the numbers.

Reset must rebuild the scene from stored initial conditions, not from current state. Keep a scene factory:

function buildScene(name) { /* returns a brand-new World */ }

let world = buildScene("billiards");
document.getElementById("reset").addEventListener("click", () => {
  world = buildScene(currentScene);
  E0 = world.totalEnergy();     // re-baseline the drift readout!
  acc = 0;  last = 0;
});

4   Visual Design That Teaches

💡 The rule for every visual choice: does it reveal physics? A drop shadow doesn't. A velocity arrow does. A gradient background doesn't. Coloring bodies by kinetic energy does. Polish in a physics simulation means legibility, not decoration. Ask of every effect: "what can a viewer now understand that they couldn't before?"

// Color by speed — instantly shows energy distribution in a gas of particles
function speedColor(v, vMax) {
  const t = Math.min(v / vMax, 1);
  const hue = (1 - t) * 220;        // 220 = blue (slow) → 0 = red (fast)
  return `hsl(${hue}, 85%, 55%)`;
}
🔬 The strip chart is worth the effort. A small canvas below the main one, plotting E(t) over the last ~10 seconds, is your Lab 2 energy plot rendered live. Set e = 1 and it's flat; set e = 0.8 and it steps downward at every collision; switch to plain Euler and watch it curve upward. You've turned an abstract numerical-methods result into something a viewer sees happen.

5   Publishing on GitHub Pages

5.1   Turning it on

  1. In your phys311 repo: Settings → Pages
  2. Source: Deploy from a branch → main → / (root) → Save
  3. Wait 1–2 minutes for the first build
  4. Visit https://<username>.github.io/phys311/labs/lab10/
⚠️ The four deployment failures, in order of frequency.
  1. Case sensitivity. GitHub Pages runs Linux; your laptop probably doesn't. import { Vec2 } from "./Vec2.js" works locally and 404s in production if the file is vec2.js. Pick all-lowercase filenames and never think about this again.
  2. Absolute paths. src="/engine/world.js" resolves to the domain root, not your project folder. Use relative paths: ./engine/world.js.
  3. Forgot to push. It works locally because the files are on your disk. Run git status — is everything committed and pushed?
  4. Browser cache. Your update is live but you're seeing the old version. Hard-refresh with Ctrl/Cmd+Shift+R, or check in a private window.

5.2   Documentation is part of the deliverable

Someone will land on your page with no context. Your README (and a short blurb on the page itself) should answer:

  • What is this? One sentence a non-physicist understands.
  • What physics does it implement? Forces, integrator, collision model, restitution.
  • How do I use it? Controls table — every key, button, and slider.
  • How do I know it's right? Your validation evidence: conservation results, drift figures, tests you ran.
  • What are its limits? 2D only, no rotation, tunneling above x m/s, whatever is true.
💡 The "how do I know it's right?" section is what makes this physics. Anyone can post a bouncing-ball animation. Stating that momentum is conserved to 10−14 over 10,000 collisions, and that energy drift stays under 0.01% for 60 s with Verlet, is the difference between a toy and a scientific artifact. Every graded project in this course is expected to make that claim — and back it up.
